# Décisions et risques acceptés

*Cadrage §8–§9 — index : [README.md](README.md).*

## 8. Conditions de l'acceptation du risque GitLab

À vérifier une fois, puis à re-vérifier si l'organisation du projet change.

**Fermeture de S10.** Le wrapper pousse les branches d'agent avec
`--push-option=ci.skip` (`-o ci.skip` en git ≥ 2.18). C'est un contrôle appliqué
**au push par le wrapper**, qui est fiable : l'agent ne pousse jamais lui-même et
ne peut donc pas le retirer. Le contraire — un `workflow:rules:` dans
`.gitlab-ci.yml` — vivrait dans le dépôt, sous contrôle de l'agent (S06/S09), et
ne convient pas. Un push `ci.skip` crée un pipeline marqué *skipped* qui
n'exécute aucun job ; combiné à la condition 2 ci-dessous (branche non protégée),
aucune exécution CI n'a lieu avant que l'owner ne lance le pipeline
manuellement, après relecture — moment où R3 gouverne.

*Vérification* : pousser une branche d'agent via le wrapper ne crée aucun
pipeline exécutant un job.

Conditions résiduelles, pour le pipeline que l'owner lance **délibérément** après
relecture :

1. Toutes les variables sensibles sont marquées **Protected**. Attention : *Masked*
   n'est pas *Protected* — le masquage ne fait que caviarder les logs, le job lit
   quand même la valeur.
2. Aucun motif de branche protégée ne couvre les branches d'agent (condition dont
   dépend aussi la fiabilité de `ci.skip`).
3. L'allowlist de `CI_JOB_TOKEN` est connue. Résidu assumé : minutes CI
   consommées, et publication possible dans le registry de paquets du projet.

Note : l'agent n'ayant aucune route vers GitLab, il ne peut pas lire le
résultat de son propre pipeline. Pas de boucle de rétroaction.

## 9. Décisions

Les décisions ouvertes des versions précédentes sont tranchées ici. Une reste
différée (D5), pour la raison indiquée.

| # | Décision | État |
|---|----------|------|
| D1 | Authentification de l'agent auprès de l'API Claude (R2, R9) | **Tranchée — broker autonome.** Un service local **indépendant du wrapper** (démon, cycle de vie propre) détient le jeton d'abonnement (`setup-token`) pour toute sa durée de vie. Deux faces (R9) : une **face de contrôle** locale (socket) où le wrapper frappe et révoque une **capability par run** (portée, budget, expiration) ; une **face de données**, cible de `ANTHROPIC_BASE_URL`, liée à la seule interface de la sandbox, où le Claude Code de la sandbox envoie ses requêtes en portant la capability via `ANTHROPIC_AUTH_TOKEN`. Le wrapper est **client** du broker, ne détient jamais le jeton réel, et ne détruit que la sandbox (R5) ; le broker survit au run. Le `setup-token` étant limité aux requêtes de modèle, l'écart de portée avec une clé Console scopée est faible ; le plafond de dépense manquant est fourni par le broker (R4, R9). **Validé** : le trafic authentique de Claude Code franchit l'authentification à travers un relais transparent qui ne réécrit que l'`Authorization`, flux SSE sans mise en tampon compris. Le verrou de signature existe bien (le jeton n'est honoré que pour un trafic reconnu comme Claude Code, « only authorized for use with Claude Code »), mais le relais transparent le franchit *par construction*, puisque c'est réellement Claude Code qui s'exécute dans la sandbox — le broker ne fait que transporter sa signature (en-têtes, user-agent) sans l'altérer. **Restent ouverts** : un run agentique multi-tours réel (dernière vérification de conformité, pas encore faite) ; le comptage d'usage en flux ; et la veille sur un durcissement éventuel de la détection amont, qui se manifesterait en `429` sans en-têtes `anthropic-ratelimit-*` (canari) et forcerait le repli sur clé Console scopée + workspace vide (S28). |
| D2 | L'historique git complet est-il acceptable dans la boîte (S15) ? | **Tranchée — oui.** L'historique complet entre dans la sandbox. Les secrets qui y traînent relèvent du risque accepté S15, cohérent avec S30 : la confidentialité du dépôt n'est pas protégée. Pas de clone superficiel. |
| D3 | Identité des commits produits par l'agent (S19) | **Tranchée — auteur dédié.** Auteur/committer git dédié (bot), jamais l'identité du propriétaire du poste. **Aucune signature avec une clé du poste** : signer les commits de l'agent détruirait la non-répudiation que S19 identifie. |
| D4 | Emplacement et format de la configuration du wrapper (S08) | **Tranchée — hors dépôt.** La configuration du wrapper vit hors du dépôt cible : S08 est fermé par absence (P2), le wrapper ne source rien du dépôt (R6). En revanche `CLAUDE.md`/`AGENT.md` vivent **dans** le dépôt comme entrée légitime de l'agent, lue dans la sandbox. Leurs modifications, comme `.claude/` et `.mcp.json`, sont traitées par R7′ (alerte pour l'instruction, blocage pour l'exécutable) car elles atteignent le poste à la prochaine session normale (S09). Partage tâche / régime (P0) : le `CLAUDE.md`/`AGENT.md` du dépôt porte le **non vérifiable** — ton, consignes, intention — libre et non fiable ; le **vérifiable** — schéma de réponse, accès, bornes — vit dans le prompt système injecté par le wrapper, souverain, et **prime en cas de conflit**. |
| D5 | Valeurs par défaut des plafonds R4 | **Différée — à définir en implémentant.** Les quatre plafonds (CPU/RAM, disque, durée, tokens) et leurs pendants côté récepteur et broker seront calibrés sur des runs réels. R4 et sa vérification restent l'exigence ; seules les valeurs sont différées. |
| D6 | Famille d'isolation | **Tranchée — micro-VM native, Apple `container`.** Sur un hôte macOS Apple Silicon, `container` (1.0, adossé à Virtualization.framework) donne une micro-VM par run : R1 et R5 par **absence** (le `$HOME` du poste n'est pas monté — P2), R4 nativement (CPU/RAM/disque comptés par VM), frontière à l'**hyperviseur** et non au noyau partagé (§10, annexe). Images OCI standard → l'environnement de dev vient d'une image dont on contrôle exactement le contenu (rien du poste). **Contrainte** : macOS 26 + Apple Silicon. **Repli** si le poste n'est pas sur macOS 26 : Tart ou Lima (mêmes fondations Virtualization.framework, micro-VM). **Pourquoi pas Firecracker**, pourtant la référence micro-VM côté serveur : il pilote KVM et exige un hôte Linux ; sur Mac il ne tourne qu'imbriqué dans une VM Linux (deux couches d'hyperviseur, une VM Linux permanente à entretenir) pour le **même** modèle d'isolation, et ses mainteneurs ne prévoient pas de support macOS. Firecracker redevient le bon choix si la sandbox migre un jour sur un runner Linux. |
| D7 | Confidentialité du dépôt (S30) | **Tranchée — risque accepté.** Le code et la spec sont exfiltrables ; on l'accepte pour garder P1 (internet gratuit). **Condition de révision** : si un dépôt contenant du code confidentiel entre dans le périmètre, P1 est réévalué — allowlist réseau stricte ou coupure du canal sortant — au prix de l'ergonomie. |
| D8 | Plan de contrôle — comment un run est déclenché | **Tranchée — aucune surface réseau entrante sur le wrapper.** Le wrapper est un binaire qu'on invoque (CLI), pas un service qui écoute ; le broker n'a qu'un socket local et une face de données vers la sandbox. Le déclenchement distant (webhooks GitLab/GitHub) vit dans un **projet amont dédié**, séparé, dont c'est le seul rôle : il porte la surface réseau entrante, la vérification de signature du webhook, l'identité de forge et les plafonds (fréquence, concurrence), et n'a qu'un droit sur le wrapper — l'**invoquer**, par tableau d'arguments validés (jamais une ligne de commande concaténée, R6). Le contenu d'un webhook est une **entrée hostile** (quiconque ouvre une MR le déclenche) : l'amont ne passe au wrapper que des données structurées et validées (dépôt, SHA, demandeur), jamais du texte libre recopié. Cette séparation garde au wrapper sa propriété « aucune porte » et rend le déclencheur remplaçable (Slack, autre forge) sans y toucher. |
| D9 | Image de la sandbox (R1, R2, §11) | **Tranchée : base Debian, Claude Code natif épinglé, utilisateur dédié.** Définition dans `images/sandbox/` (Dockerfile commenté, README qui tient lieu de spec détaillée). **Base** : `debian:trixie-slim` linux/arm64, épinglée par digest d'index. Debian est une cible documentée de Claude Code et repose sur la glibc : le binaire natif et le ripgrep qu'il embarque tournent tels quels, et les couches d'outillage à venir (Go, Node) visent aussi la glibc. Alpine, plus petite de quelques dizaines de Mo, imposerait musl (`libgcc`, `libstdc++`, ripgrep système, `USE_BUILTIN_RIPGREP=0`) à chaque couche ; l'écart de taille est négligeable devant les 332 Mo du binaire. **Installation** : téléchargement direct du binaire natif (`claude-code-releases/<version>/linux-arm64/claude`) dans une étape de build séparée, vérifié contre le SHA256 publié dans le manifeste signé de la release (signature contrôlée par le mainteneur au moment d'épingler, procédure dans le README). Ni le script `install.sh`, qui télécharge d'abord la dernière version puis laisse un lanceur et un répertoire de versions sous `$HOME`, ni le paquet npm, qui n'enveloppe que le même binaire et ajouterait Node. **Épinglage** : base par digest, Claude Code par version exacte (2.1.236, canal stable) plus SHA256, `DISABLE_UPDATES=1` dans l'image pour que ni la mise à jour en arrière-plan ni `claude update` ne remplacent la version à l'exécution. Les paquets apt (`git`, `ca-certificates`) ne sont pas épinglés : limitation acceptée et documentée, le digest de l'image effectivement construite se lit par `container image inspect`. **Utilisateur et chemins** : Claude Code refuse `--dangerously-skip-permissions` sous root, donc utilisateur `agent` (uid et gid 1000, shell bash), `$HOME` = `/home/agent` créé vide (aucun `.bashrc` ni `.profile`, rien qui source quoi que ce soit), dépôt dans `/work`, hors de `$HOME` pour que celui-ci ne contienne que ce que le run y écrit. Ces trois noms sont le contrat du transport du dépôt. **Outils courants** : outre `git`, la base embarque `curl`, `jq`, `patch`, `procps` et `python3`. Ils ne sont pas nécessaires à Claude Code ; ce sont les commandes que le modèle prend spontanément, mesurées sur l'historique Claude Code du propriétaire (`python3` au niveau de `cat` et `sed`, devant `grep`). En mode non supervisé, un outil absent coûte du contexte et parfois le run, ce qui vaut plus que quelques dizaines de Mo. Une seconde image plus sobre a été écartée : aucun cas d'usage ne fonctionne mieux avec moins. Les runtimes et linters (Go, Node, golangci-lint) restent dans les profils. **Règle d'installation** : pas de sudo. Le harnais fournit ce que la définition de fini du projet exige (runtime, gestionnaire de paquets, linters), épinglé dans un profil ; l'agent installe le reste en espace utilisateur à l'exécution, avec internet, et cela disparaît avec la VM. L'image qui tourne reste celle que le Dockerfile décrit, l'agent garde l'autonomie de faire et pas seulement de voir. **Absent par construction (P2)** : aucun identifiant, aucun chemin du poste, aucun profil de shell, aucun index apt, pas d'`ENTRYPOINT` ; `~/.ssh`, `~/.aws`, `~/.claude`, `/Users` et `/private` n'existent pas, ils ne sont pas interdits. **Construction et stockage** : `container build` depuis `images/sandbox/`, étiquette `cove-sandbox:local` (sans la version, pour ne pas toucher `AGENTS.md` à chaque bump ; la version est dans `claude --version` et le label OCI), dépôt d'images local uniquement, pas de registre. **Extension** : une image de projet part de `FROM cove-sandbox:local`, ajoute sa chaîne d'outils en root, revient à `USER agent`, garde `/home/agent` vide et repasse les commandes d'acceptation ; non implémentée ici. **Pas de script de vérification** : les garanties de l'image sont structurelles (P2), le Dockerfile ne copie rien du poste, fixe un utilisateur non root, crée un `$HOME` vide et ne porte aucun identifiant ; le build échoue si le checksum épinglé ne correspond pas, et Claude Code refuse lui-même de démarrer en root. Un script écrit pour cette issue a été retiré : chacun de ses contrôles testait le Dockerfile contre lui-même avec des listes de chemins et de motifs, la forme de liste que P2 écarte. Ce qui peut encore défaire R1 et R2 n'est pas l'image mais son lancement (`--volume`, `-e`, `-u`) : c'est le tableau d'arguments du wrapper, testé en Go dans l'issue qui l'introduit. |
| D10 | Ce que `container` offre pour piloter la sandbox (R5, R8, R9, §12) | **Tranchée : CLI `container` par tableau d'arguments ; MVP interactif faisable avec l'image épinglée ; hôte joignable seulement sur la passerelle du réseau de la VM ; canal entre VMs fermé par un réseau par run, LAN fermable par netfilter dans l'invité ; ni disque ni durée bornés par un drapeau. Broker (D1) et transport (R8) hors de cette décision : pour l'instant la VM parle directement à l'API Anthropic.** Observé le 7 septembre 2026 : `container` 1.3.1 (`container --version`), macOS 26.5.2 (`sw_vers`), noyau kata 6.18.35 (`container system property list`), image `cove-sandbox:local`. Où l'aide et l'observation divergent, l'observation prime. **1. Pilotage.** CLI plutôt que framework : l'apiserver n'est joignable qu'en XPC (`apiserver.plist`) et Containerization est un paquet Swift, hors de portée de Go sans cgo. JSON sur `list --format json`, `inspect`, `stats`. Tout échec du CLI sort 1 avec `Error:` sur stderr, comme un `exit 1` de l'invité : indiscernables par le nombre. Le code du processus 1 devient celui de `run` (`sh -c 'exit 7'` sort 7 ; 137 si `kill`, `stop` après délai, `delete -f` ou l'OOM killer le frappent). `start` et `stop` sont idempotents (0) ; `delete` refuse une VM en marche sauf `-f` ; image absente : `run` interroge `docker.io` et échoue en 401, d'où `image inspect` avant ; `exec` tourne sous l'utilisateur et le répertoire de l'image (`exec xfer id` : uid 1000 ; `pwd` : `/work`), `-u root` donne root ; `logs` rend le stdio du processus 1, pas celui des `exec`. Orphelins : la VM appartient à un service launchd (`launchctl list` : `container-runtime-linux.<nom>`) ; `kill -9` du CLI la laisse tourner (`container list` : `running`), `--rm` compris ; SIGINT ou SIGTERM au CLI est une erreur XPC (`failed to send signal`) et la VM continue. Sa destruction est un verbe explicite (`stop` puis `delete`, ou `delete -f`), jamais un effet de bord. `appRoot/containers/<nom>/` disparaît au `delete` ; un nom unique ne laisse aucune trace (`grep -rl zq7xk` hors magasin d'images : rien). **2. Réseau.** Adresse dans `192.168.64.0/24` (`network inspect default` : NAT vmnet, passerelle `192.168.64.1`), séquentielle et non réutilisée, donc à lire dans `list --format json` après démarrage. Côté hôte `bridge100` (`192.168.64.1/24`), partagée, un `vmenetN` par VM (`ifconfig bridge100`), qui n'existe que pendant qu'une VM tourne (toutes arrêtées : `does not exist`, `bind` : `errno 49`). Un listener lié à `192.168.64.1` répond à la VM (200) et est refusé depuis l'adresse LAN de l'hôte et `127.0.0.1` (`curl` : `Couldn't connect`) ; lié à `0.0.0.0`, la VM le joint aussi par l'adresse LAN de l'hôte : un service pour la sandbox lie la passerelle, jamais `0.0.0.0`. Non vérifié depuis une seconde machine du LAN. L'hôte ne joint pas la VM (`nc -vz` : `No route to host`). LAN et internet joignables (`curl -I http://192.168.1.254/` : 200 ; `https://example.com` : 200) : S32. `--internal` coupe tout, passerelle comprise (`connect_ex` : 11), écart avec « host-only ». Deux VMs du même réseau se joignent (200) ; deux réseaux NAT (`network create --subnet 10.77.0.0/24`) s'ignorent (délai dépassé) : un réseau par run isole les runs. Filtrage dans l'invité : netfilter est dans le noyau (`zcat /proc/config.gz` : `CONFIG_NF_TABLES=y`) mais `CAP_NET_ADMIN` manque, même à `exec -u root` (`nft list ruleset` : `Operation not permitted`). Avec `run --cap-add NET_ADMIN` et `nftables` dans une image jetable, une table `inet` sur `output` (passerelle acceptée, plages privées v4 et v6 rejetées), posée par `exec -i -u root nft -f -`, donne en uid 1000 : internet et passerelle ouverts (`example.com` 200, `deb.debian.org` 30 Mo/s), routeur, adresse LAN de l'hôte et VM voisine fermés (`curl: (28)`) ; l'agent ne lit ni ne défait les règles (`nft list ruleset` : `Operation not permitted`, `CapEff 0`, root verrouillé dans `/etc/shadow`). Test de fraîcheur (P4) : `example.com` répond, le routeur échoue. Exige `nftables` dans l'image (D9, suivi ; `images/sandbox/` intact), `--cap-add NET_ADMIN` au lancement et `-u root` réservé à l'`exec` qui pose les règles. DNS (S01) : `nameserver 192.168.64.1` (`cat /etc/resolv.conf`), relais du NAT, aucun processus hôte sur le port 53 (`lsof -iUDP:53`) ; `--no-dns` laisse le `1.1.1.1` de la base Debian. **3. Octets sans montage.** `cp`, stdin de `exec -i`, stdout de `exec`, réseau VM vers hôte seulement ; tous exigent une VM en marche (`is not running`). `cp` écrit en root (`ls -la` : `root root`), `exec` sous l'utilisateur de l'image. 300 Mo, SHA256 vérifié : `exec -i` 0,84 s, `exec` stdout 0,69 s, `cp` 0,71 s et 0,54 s ; HTTP depuis l'hôte 0,29 s au repos mais 6 min 49 s une fois sous charge, inexpliqué. Git : bundle par stdin puis `git clone` dans la VM ; `git fetch` de l'hôte avec `exec -i` comme transport (`GIT_SSH_COMMAND` vers `container exec -i xfer sh -c "$*"`) en 10 s ; `git bundle create -` sur stdout passe `bundle verify`. Faisabilité seulement, le transport reste à choisir. **4. Terminal.** `-it` sur `run` et `exec`, pas d'`attach` ; TTY hôte requis (`Operation not supported by device` sinon). PTY invité (`tty` : `/dev/pts/0`), taille propagée (`stty size` après `TIOCSWINSZ`), `TERM=xterm` sauf `-e TERM`. Octets bruts : une séquence OSC de l'invité arrive intacte. Ctrl-C va au processus invité (`trap` exécuté, `exec` vivant). `exec -it -w /work net-a claude` : `Welcome to Claude Code v2.1.236`, `/home/agent/.claude` créé sous `agent`, `/work` intact : MVP faisable, contrat D9 inchangé. **5. Ressources.** `--cpus` (défaut 4) et `--memory` (défaut 1 Go) : l'invité voit N+1 processeurs (`nproc` : 5 ; 2 avec `--cpus 1`) et la mémoire plus 100 Mo (`MemTotal`). Dépassement mémoire : OOM kill, 137. CPU confiné au nombre de vCPU (`stats` : 104 % avec quatre boucles sur `--cpus 1`). Disque : aucun drapeau, rootfs creux de 513 Go (`ls -la rootfs.ext4` ; `du` : 1,7 Go), `delete` rend l'espace. Durée : aucun drapeau (`run --help`). Les deux se tiennent hors de `container`, D5 les calibre. Démarrage : 3 à 5 s. |
